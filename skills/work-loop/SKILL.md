# Work loop

GitHub is the only durable work state: issues are work, native issue dependencies express blocking, and pull requests show work in flight. Repository-local instructions, conventions, tests, and architecture remain authoritative.

**Default: one worker in the repository checkout.** At most **one active implementation worker per repository**. It works in that repository's ordinary directory on a task branch, owns the scope from acceptance handoff through PR completion, and resumes existing active work before starting another implementation in that same repository. Do not create or clean up worktrees as routine orchestration. Independent acceptance authoring and implementation remain distinct contexts, but operate **sequentially**, not as competing writers; reviewers can inspect without owning another implementation. Different repositories can be visited independently without shared claims, reservation state, or parallel implementation inside a repository. A new worker may take over only after the earlier worker stops and hands off its exact branch/PR.

Do not add claims, queues, coordination files, per-repository loops, or status labels. The only workflow label this loop uses is `needs-decision`.

Use `node ~/.local/share/coding-agent/workctl.mjs` for deterministic PR scanning, readiness, and guarded merges.

**Design precedes execution:** A new product or major feature should pass through `grill` and repository-owned decisions **before** implementation issues are written. This loop consumes approved issue scopes; it must not choose missing product direction during coding. Existing well-specified features, routine bug fixes and behavior-preserving refactors require no new grilling ceremony.

## Session focus and shutdown

- Treat an owner's selected repository/journey and stop condition as the session boundary. Record the selected observable outcome and its evidenced blockers on the owning issue; keep that journey as the worker's focus through implementation and release. Necessary upstream dependencies and evidenced urgent correctness/security regressions remain eligible with a recorded reason and normal acceptance/ownership rules. Routine unrelated maintenance does not interrupt an active journey merely because a scan finds a broken or ready PR.
- Apply “finish existing work first” within that focus. An unscoped initial scan may reconcile existing work across repositories; it does not authorize repeatedly widening a selected journey or treating every newly arriving dependency PR as today's work. When a prerequisite makes the visible outcome larger than the selected slice, state the delivery gap rather than counting the enabler as completion.
- When the owner says to finish the current issue and stop, freeze the issues/PRs already in flight and send that boundary to every worker. Finish their current fixes, required validation and available publication; do not select another issue, prepare the next feature, or silently grow the shutdown set into another prerequisite chain. Record newly discovered blockers as handoffs. If only external CI/review/deployment remains, leave the work open with the exact PR/head, completed evidence and pending gate, then stop without polling. Never waive a gate or claim completion to satisfy shutdown.
- Outside shutdown, a waiting PR permits another worker/repository only within the owner's remaining scope. If no in-scope work is actionable, report the handoff rather than inventing maintenance to stay busy. Do not create a separate scheduler, session ledger or state file.

## Loop

1. **Finish existing work first.**
   - At each natural scan, reconcile original feature issues with a recorded **Awaiting live deployment verification** handoff, including **closed issues**. Search issue comments across both open and closed states, rather than relying on the open-PR scan. Read the latest evidence to distinguish pending from already verified handoffs; inspect each pending handoff's referenced PR for merged state and merge SHA even if that PR has disappeared from `workctl scan`. Once merged, verify the deployed revision and specified owner journey; reopen an automatically closed issue while evidence is pending, stale, unavailable or failing, and close it only with live acceptance evidence. An unmerged queued PR remains pending. GitHub issue comments are the durable handoff, not a new queue or label.
   - Run `workctl scan` before starting an issue. Repair in-scope `broken` work and leave `waiting` open; defer unrelated routine maintenance under the session-focus rule above. If a global scan stalls, preserve its error/partial result and use bounded repository/PR queries; do not launch duplicate global scans or infer a clean queue from an incomplete scan. Before merging **any** `ready` PR, including one that predates this skill, inspect its actual changes and issue for behavior/architecture impact and apply the `acceptance-contract` handoff when required. `workctl` readiness proves mechanical CI/high-priority-finding/mergeability only, **not** independent acceptance. For legacy PRs with implementation already committed, use the skill's **retrospective migration handoff** rather than pretending that tests preceded implementation. If required evidence is still missing, treat the PR as waiting and resume it rather than calling `workctl merge`; merge only after both gates pass.
   - A PR whose base is not the repository default branch is `waiting`: never merge it into another feature branch. For legacy stacked PRs, merge the base PR first, then retarget the child to the default branch and revalidate it.
   - Resume existing agent work when it can be traced to an open PR or issue. Discard stale agent-owned work only when its work is closed or superseded. Never overwrite unrelated user changes.

2. **Pick one actionable issue from product evidence.**
   - Skip `needs-decision`, bot/meta issues, issues with open native `blockedBy` dependencies, and issues already represented by an open closing PR.
   - Before comparing candidate repositories, scenarios or blocker issues, consult each candidate repository's current applicable Atlas Decisions and Questions when an Atlas exists. Use scoped `daq find` / `daq get` / `daq questions`; when queries are unavailable or their index may be stale, read the authoritative current Markdown. Current Decisions control which declared scenario is eligible and its priority; retired or superseded roadmap, test or Atlas text cannot establish selection priority. Consider Questions only when they materially affect this selection; unresolved consequential direction follows the evidence-gap/owner-decision path below. Without an Atlas, use current owning product documentation and owner decisions.
   - After finishing existing PRs and resolving current intent, inspect each candidate repository's **declared highest-priority product acceptance scenario** and its last recorded outcome. Reference its existing scenario/test and evidence (input, revision, result and limitations where recorded); a closed issue or green internal test is not a substitute. Product intent and acceptance stay in the owning repository's existing documentation and tests.
   - For a failing scenario, choose the earliest **actionable, evidenced blocker** along that user journey. Prefer its existing GitHub issue; create a focused issue only when needed, using `issue-preflight`. Follow native dependencies to an actionable prerequisite rather than starting a blocked acceptance issue. Do not prefer optional micro-optimizations merely because they are easy or recent.
   - If an executable scenario or reliable outcome is missing, explicitly record that evidence gap. Prioritize independently specifying a minimal representative scenario/fixture and separate acceptance-test authorship in the owning repository, using `issue-preflight` and `acceptance-contract`, before optional implementation. Do not fabricate a fixture result, infer freshness or priority, or introduce a score to replace missing evidence. If the repository has no declared priority and existing intent does not settle it, use `grill`/an owner decision rather than inventing one.
   - Urgent correctness regressions and security defects remain eligible to supersede feature blockers. Record the severity/evidence and why the chosen issue takes precedence; do not force urgent maintenance behind feature work. For remaining maintenance, use existing dependencies and repository intent to explain the choice.
   - Across repositories, apply established owner priorities, evidenced dependencies and urgent severity first. If multiple evidenced, actionable blockers remain with no supported ordering and choosing among them has no consequential product trade-off, schedule the oldest actionable blocker issue by GitHub `createdAt`, then repository full name and issue number for exact ties. Record this as a neutral scheduling tie-break, **not** evidence of superior product priority. If the choice requires a consequential product trade-off, use `grill`/an owner decision instead. This tie-break never bypasses exclusions or the missing-evidence path above.
   - Record the selected scenario/evidence, blocker or prerequisite, and reason on the owning issue or PR. Keep GitHub as execution state: no separate planner, queue, daemon, score database, coordination files, universal product-spec schema, or new workflow labels. `workctl` proves mechanical PR readiness, not product priority or acceptance.
   - If an independent end-to-end result conflicts with the intended reference experience despite green tests, invoke `grill`/an owner decision and clarify the owning product specifications before choosing more implementation work for that scenario. The implementation agent cannot weaken acceptance expectations to fit its output; use `acceptance-contract` to independently verify translations of explicit current owner decisions.
   - Treat reopened feature issues marked by a previous comment as **awaiting live deployment verification**, not as completed merely because their implementation PR merged. At the next natural scan, check the deployed revision/route and the specified owner actions: close with concrete live evidence only when verified; leave pending issues open while publishing is in progress; repair the issue if published behavior fails. Do not create another queue or polling loop.

3. **Understand the issue.**
   - Read the issue, comments, applicable repository agent instructions, relevant code, and current product intent. When an Atlas exists, use scoped `daq get` / `daq find` / `daq questions` where available, falling back to the authoritative Markdown; do not infer decisions from retired text or stale indexes.
   - For a known relevant source path, prefer `coding-tooling inspect --target <path> --json` from the repository root (repeat `--target` for multiple paths). Read its applicable instruction and convention references, reuse its focused validation commands, and retain the separate repository completion gate. Root/ancestor `AGENTS.md` and repository-local rules remain mandatory. If tooling is unavailable, the path or relationships are unknown, or inspection is partial, fall back to the repository's own instructions and conservative validation; never invent a narrowed scope or claim unrun checks passed. Do not load unrelated repository documentation when the task context is resolved.
   - If it is already done, close it with evidence.
   - Apply `issue-preflight` before implementing: verify the promised outcome against current Atlas Decisions (when present), supporting vision/ADRs, architecture and quality constraints. If a new major feature lacks owner-approved direction, park it for design-first `grill` rather than implementing a guessed MVP. Keep this lightweight for routine, well-specified work. For user-facing features, require a demonstrable vertical slice with an actual Pages route (or equivalent), owner actions, and an expected observable result; a backend-only step is a technical enabler, not feature completion.
   - If repository state settles an ambiguity, proceed and record the choice in the PR.
   - Classify whether the actual scope changes behavior or architecture. If so, use `acceptance-contract` to establish independent, repository-owned verification before production edits. Existing tests only suffice if an independent acceptance agent confirms their coverage.
   - If a consequential owner decision is still needed, record or reference its Atlas Question when applicable, add `needs-decision`, and move to other actionable work; invoke `unblock`/`grill` one question at a time when the owner is available. Do not make implementation decisions on the owner's behalf.

4. **Implement one coherent scope.**
   - Use the repository's ordinary checkout and a task branch by default. Inspect its Git state before switching branches; resume the existing task branch/PR, or start a new task branch from the freshly fetched default branch. Preserve unrelated user changes. Use an existing isolated checkout or a worktree only when a concrete isolation need or unrelated checkout work prevents safe in-place work, and record the reason. Never stash, reset, overwrite or discard user changes to force a clean checkout.
   - For behavior/architecture changes, establish or independently verify acceptance with a **separate acceptance agent/context** before any production edits. If tests change, commit them before implementation. If existing tests already suffice, record their paths, baseline revision and independent verification on the issue **before** implementation; no empty or artificial test commit is required.
   - Push early and open a draft PR with `Closes #<n>` as soon as the acceptance change or another meaningful pre-implementation change can form a PR, **before** the implementation agent begins. If no pre-implementation file change is warranted, retain the earlier issue handoff, open the draft with the first meaningful implementation commit, and immediately link that pre-implementation handoff; never invent a dummy change. Always target the default branch; never create stacked PRs. If the next slice depends on an unmerged PR, leave it as an issue and work elsewhere until that PR lands.
   - Implement in a distinct agent/context using the established acceptance contract. If independence cannot be arranged, leave an existing task PR in draft awaiting handoff; when no draft or meaningful commit exists, record the missing handoff on the owning issue and do not begin implementation. Never manufacture a commit to create a placeholder PR.
   - **Flat queue with honest handoffs:** If the original issue is broader than one coherent PR, finish and verify a bounded useful slice, then create or reuse **small successor issues for every remaining required behavior** with exact evidence gaps and their source: Decision Atlas IDs when the repository has an Atlas, otherwise links to the current owning product documentation or owner decisions (never invented IDs). Record the delivered scope and successor links in the original issue. Close it as `not_planned`/superseded when its original acceptance is *not* fully delivered, or as `completed` only if that acceptance actually passed. The durable product goal stays in the hierarchical Decision Atlas (or, without one, the owning product documentation); GitHub issues should remain a largely flat, short-lived execution queue, not endlessly open epics with child/grandchild chains. Before closing, reconcile any native `blockedBy` edges that pointed at the oversized issue to the **complete minimal set of successor prerequisites** that each dependent issue still needs, so it cannot become actionable while any required behavior is missing. If the tooling cannot change those edges, explicitly report the limitation and leave the blocked queue honest rather than pretending a closed parent proved the missing behavior. Never discard scope merely to get an issue closed.
   - If another repository owns a missing capability, create the smallest issue there that actually unblocks this work and add it as a native GitHub dependency. Do not implement both repositories from one issue. **Follow the dependency upstream:** a worker scoped to a repository (even when the owner names only that repository) may then work that upstream issue itself in the owning repository's ordinary checkout. It follows that repository's own instructions, acceptance, review and merge rules, uses a separate issue and PR there, and finishes or parks one implementation before starting another. When the upstream change has merged (and published, if consumers pin a release), it updates the consumer's dependency and resumes the blocked issue. Skip the upstream repository and report instead when its checkout has unrelated uncommitted changes, or when another worker owns it, unless that worker has both stopped and handed off its exact branch/PR as above. An active, stopped or rate-limited owner without that handoff keeps the repository, and a clean checkout is not proof that it is free.

5. **Validate and merge.**
   - Run the repository-documented validation for the touched scope.
   - On the first unexplained failure, preserve its raw output, command, source and relevant inputs before retrying or minimizing. Classify the failing layer (product behavior, test assertions, tooling, environment or reporting) from the original command and logs. When a narrower repro goes green, capture bounded state at the original failing boundary before more uninstrumented repeats: relevant operation/connection identity, lifecycle, pending work and observed result. Redact secrets; unavailable state stays unknown. Diagnostic repeats test hypotheses and cannot clear a failed deterministic gate.
   - Trust ordinary repository setup. When a concrete failure identifies missing tools/libraries or broken native links, repair that environment and use a cheap representative compile/link/runtime probe before repeating the expensive gate. A metadata-only probe does not prove linking or execution; do not impose fingerprints, runner receipts or universal containers on successful normal runs.
   - Preserve raw failure reports; write subsequent runs separately. Prefer the canonical `coding-tooling run --report` collector where applicable instead of ad hoc status parsers. Record actual executed/pass/fail/skip counts for required acceptance tiers: exit 0 with no required cases executed is missing evidence. Keep legitimate optional skips distinct. Report per-command results separately from wrapper/bookkeeping failures, and repair every required failing gate in its owning layer before calling overall validation green.
   - Keep the source identity recorded by the original run. If tested uncommitted files are later committed, independently establish their byte identity rather than relabeling the old run as a new-head execution. Re-run checks invalidated by later changes; uncertain impact still requires the full applicable suite. If only an excerpt of a lost log remains, label the evidence incomplete rather than reconstructing a raw log.
   - Keep one-shot Rust verification disposable. When installed, wrap the repository's verification command with `python3 ~/.local/share/coding-agent/disk-maintenance.py run -- <command>`. It supplies a private `CARGO_TARGET_DIR`, disables incremental compilation, preserves a free-space reserve, and cleans output on success, failure and cancellation. Preserve compact reports outside the temporary target before exit. Respect repository commands that explicitly own their target directory or exported build artifacts; use their equivalent cleanup lifecycle rather than claiming the wrapper controls an overridden target. Routine iterative development may reuse its normal target. Do not retain task-specific verification targets or dependency backups after completion; source checkouts and irreplaceable evidence remain separate from disposable output.
   - For user-facing feature PRs, exercise the integrated user journey through the real frontend in a production-like build/preview, record the Pages/demo entrypoint and owner reproduction steps, and provide browser acceptance evidence. A passing API test or isolated mock UI is insufficient. If Pages deploys only after merge, record the planned public verification separately from the pre-merge preview evidence; do not claim the public route is verified yet.
   - Gate merge on new or independently verified existing acceptance contracts, executable architecture invariants, and core smoke checks. Use a deterministically proven affected-test selection only when its dependency mapping is complete; otherwise run the full applicable suite and record the gap. Verify periodic full-suite coverage and record a follow-up if absent. Do not weaken expected behavior to fit an implementation; explicit current product specifications control test expectations, with independent verification of test translations. Independently reverify harness/fixture changes that could alter what a test exercises, even if assertions are unchanged.
   - **Before requesting a feature merge, enabling auto-merge or admitting it to a merge queue:** when live verification depends on post-merge publication, record **Awaiting live deployment verification** on the original feature issue, including the PR URL/head SHA, demo route, owner steps and expected outcomes. Do this before GitHub can automatically close the issue. The next natural scan must find this handoff even if the issue is closed and the PR has already merged; a queued merge request is not a completed merge or deployment.
   - Re-run `workctl pr <repo>#<n>` for the touched PR: repair `broken`, leave `waiting`, and invoke `workctl merge` only for `ready`.
   - **After a successful feature merge, before returning to the loop:** if the promised user-facing demo publishes only after merge, check the actual Pages workflow/deployment and exercise the published route against the issue's owner actions and observable outcomes. Confirm the deployed revision where possible; a green build or reachable homepage alone is insufficient. If verified, record the public URL, revision/evidence and result on the original feature issue. If publishing is not complete, the route cannot be checked, or the result is absent/stale/broken, **reopen (or leave open) that same feature issue** with a comment naming the merge SHA, demo route, owner steps and pending or failing evidence. This preserves work in GitHub until the next natural scan can verify or repair it. Do not wait/poll for deployment, invent a queue or status label, or declare the feature complete merely because GitHub automatically closed its issue on merge.
   - Existing stacked PRs are migration state only: after their base lands, retarget them to the default branch before validation or merge.
   - Never request `@codex review` for PRs authored by `renovate[bot]`. Documentation-only, formatting-only, and mechanical dependency or CI changes likewise do not warrant AI review. CI, mergeability, independent acceptance and confirmed defect obligations still apply.
   - For substantive behavior, API, storage, security or architecture changes, **prefer one targeted Codex review** after implementation and documented validation. Name concrete risky files, contracts and failure cases. Do not request exhaustive reviews or review every intermediate commit. Review is advisory, **not a mechanical merge gate**; `workctl` reports review status without requiring its presence, completion or freshness.
   - Triage findings by reproducible impact, not solely Codex's priority label. Correct genuine security, data-integrity and acceptance defects even when labeled P2/P3. An unanswered Codex P0/P1 inline finding keeps `workctl` broken until a trusted reply documents the fix or a reasoned rejection. Verify the defect rather than automatically accepting its severity. Add focused regression protection for confirmed defects and run applicable checks. For lower-priority findings, fix when material to current acceptance, reject when false, or create a focused follow-up when deferral is appropriate; do not create work simply to silence a reviewer.
   - **No re-review loop:** a repair, CI fix, conflict resolution or changed head SHA does not by itself require another Codex review. Inspect fixes and adjacent callers/contracts for related defects, batch repairs and run focused regressions. Request another targeted review only when significant new risk arose outside the earlier review's scope, with a clear reason and narrow changed surface. Never iterate merely for a fresh SHA or an empty review.
   - **Narrow exception to the `ready`-only merge rule in steps 1 and 5:** when GitHub Actions cannot run for a repository because of an account billing or spending-limit failure (common for private repositories), first confirm that **every** failed or missing check is individually a billing/spending-limit startup failure (its annotation says so); any other failed check, including external CI or an Actions job that did start, keeps the PR `broken` and must be repaired normally, and any other queued or in-progress check keeps it `waiting` until it completes successfully. Then run every job of the repository's workflows locally against the PR head, preferably with `act` (one job at a time); fall back to running a job's steps manually when `act` cannot. Skip only jobs that need unavailable secrets or GitHub-hosted services, and say so. Record the commands, head SHA and results in a PR comment and treat a green local run as the CI gate. `workctl` will still report failed checks, so merge with plain `gh pr merge` only when the billing-attributed checks are its sole failure reasons, no other check is pending, and every other gate (high-priority findings, mergeability, acceptance) passes; never use `--admin`, and leave the PR open for the owner if branch protection refuses the merge.
   - Never sit waiting on a Codex review or CI. Once a PR's implementation is complete and it waits on CI or an optional targeted review, continue an actionable issue in a different repository only when the session-focus/shutdown boundary permits it. Otherwise record the pending handoff and stop. Re-check waiting PRs with `workctl pr` at natural breakpoints (after a push, before picking the next in-scope issue), rather than polling. A worker finishes its current implementation scope before taking another; separate workers may visit different repositories within the owner's session concurrency limit, with one implementation worker per repository.

6. **Repeat** from step 1 while in-scope work is actionable and the owner's stop condition has not been reached.

## Usage limits

- Run unattended loops in an open interactive session with Claude Code's `autoContinueAtUsageLimit` left on (the default). The main session then waits at a usage limit and continues at the reset. Background and `-p` sessions don't wait, and neither does any session whose reset is more than 24 hours away (typically the weekly limit).
- Delegated workers do not wait. A limit ends them with a rate-limit error. When the main session continues after a limit, or the owner says it has reset, check every worker before doing anything else. Resume each one that ended on a rate limit through its existing agent (not a fresh one), so it keeps its context and its repository assignment. Tell it to re-check its PRs with `workctl pr` first, because GitHub state may have moved while it was down.
- Before starting a replacement worker for the same repositories, stop the old one, so two workers never push to the same branches.

## When nothing is actionable

Invoke the `unblock` skill. Each recorded owner decision can make work actionable again. Stop when no actionable work or unresolved owner decision remains.

## Report

Throughout selection and at the end, distinguish these three evidence claims:

- **Implementation:** issue/PR state and the changes actually delivered.
- **Capability:** behavior demonstrated by named checks, with their input, revision and limits; internal tests or a fabricated fixture do not establish a real-input user journey.
- **User-observable acceptance:** the declared scenario's actual recorded independent end-to-end outcome, or explicitly **missing/unrun/stale evidence**. Never report product-level progress or a pass solely from a closed issue, merged PR, passing unit tests, or fabricated fixture. A failing end-to-end result remains failing despite green internal checks.

For policy changes, run all scenarios in `acceptance/product-selection.md` and record their semantic decisions separately from mechanical checks. This review verifies the instructions, not a consumer product outcome.

At the end, report one line per issue touched: `repo#n → merged PR #m | PR #m waiting on <x> | needs-decision | closed (reason)`, plus anything the user must do.
