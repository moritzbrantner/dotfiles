# Work loop

GitHub issues, native `blockedBy` dependencies and PRs are the work queue; the checkout also holds unfinished work. Repository-local instructions, installed conventions, Decisions, architecture and tests govern implementation. Use `node ~/.local/share/coding-agent/workctl.mjs` for PR scanning, readiness and guarded merges. Do not add coordination registries, claims, queues, per-repository loops or workflow labels other than `needs-decision`.

## Invariants

- **No discretionary priority.** Outside an owner-selected scope, choose the oldest eligible issue by creation time, repository name, then issue number. Skip bot/meta issues, active closing PRs, open native dependencies and genuine owner-only blockers. Historical roadmap stages, product-family deferrals, time/resource estimates and unrelated Atlas Questions are not blockers. Never ask the owner to rank product areas. Ask only: "Do I have what I need to implement and independently verify this issue?" Obtain or repair ordinary prerequisites yourself.
- **Respect session scope.** A selected repository/journey and stop condition bound the session. Finish its work before unrelated maintenance; necessary upstream issues and evidenced urgent security/correctness fixes may remain in scope. When told to finish and stop, freeze the issues/PRs in flight, finish available fixes and validation, and hand off pending external gates without starting more work, polling or waiving checks.
- **One active implementation writer per repository.** Use the ordinary checkout and a task branch; independent acceptance authoring and implementation use separate contexts **sequentially**. Before takeover, confirm the previous writer stopped and resume its branch/PR. A stopped or rate-limited worker does not reserve the repo forever; a PR or recent commit alone does not prove a live writer. Use an existing worktree only for a real isolation need. Never stash, reset, discard or overwrite unrelated changes.
- **PR states are handoffs.** Draft means implementation or acceptance work remains. Ready means a locally validated candidate awaiting CI/review/merge; convert back to draft before further edits. Neither state substitutes for tests or proves an agent is running. No separate handoff protocol.

## Loop

1. **Resume and finish.** Inspect branch, diff, uncommitted changes and recent commits before switching tasks. Resume recognizable unfinished work even without a PR. Run `workctl scan`: repair in-scope `broken` PRs, leave `waiting` open, and merge `ready` only after inspecting their actual diff, issue, acceptance, head, checks, findings and mergeability. Workctl readiness is mechanical, not independent product acceptance. For older behavioral PRs lacking a prior acceptance handoff, use `acceptance-contract`'s retrospective procedure; never invent tests-first chronology. If the scan stalls, use bounded repository queries; a partial scan is not a clean queue. Never merge into a feature branch; retarget legacy stacked PRs to default after their base lands. At natural scans, revisit live-deployment verification handoffs on original feature issues, **including closed issues**.

2. **Select and understand.** Finish in-scope work first; otherwise apply the neutral eligible-issue ordering above. Read the issue/comments, repository `AGENTS.md`, applicable conventions, relevant code and current product intent. Query the Atlas with scoped `daq` when available, otherwise read its authoritative Markdown. For known paths, prefer `coding-tooling inspect --target <path> --json` but retain the root instructions and repository completion gate. If the work is already done, close with evidence. Apply `issue-preflight`: preserve the approved scope and acceptance. A new major feature without approved direction goes to `grill`, not an agent-invented MVP. A user-facing feature needs an integrated, observable Pages/demo journey (or equivalent), not just a backend enabler.

3. **Resolve genuine dependencies.** Prepare missing tests, fixtures, public data, tools and licensed models as issue work. If another repository owns a prerequisite, create/link its smallest actual issue with native GitHub dependencies, implement it separately when its checkout is available, and resume the consumer after merge/publication. Never edit both repositories under one PR or contend with another writer. If a consequential owner choice, private input, credential, permission or licence is truly unavailable, record the exact blocker and applicable Atlas Question; use `needs-decision` only for an owner decision and continue other unblocked work. Ask one question through `unblock` only when necessary, without guessing the answer.

4. **Implement one verifiable slice.** Follow `issue-preflight` and, for behavior/architecture changes, `acceptance-contract` **before production edits**. A **separate acceptance agent/context** independently writes or verifies representative tests from approved intent; relate every explicit obligation to acceptance or a stated gap. Implement in a distinct context. Keep tests-first commits on the **same task branch**; record test SHA, paths, baseline result, source revision and independent context on the owning issue. If existing tests already suffice, record their paths, baseline revision and independent coverage; no empty or artificial test commit is required. Do not open an acceptance-only draft PR solely for hosted CI. Open a PR once a meaningful implementation commit exists and focused acceptance has run, linking the prior handoff. If a repository-local rule requires an earlier PR, follow that rule. Resume existing acceptance-only draft PRs on their original branches. Push coherent milestones rather than every edit; target the default branch and do not create stacked PRs. If independent authoring cannot occur, record that missing handoff and leave implementation unstarted or its existing PR in draft.
   If one issue is too broad, verify a coherent slice and create/reuse successors for **all** remaining obligations. Link their product sources and reconcile every native `blockedBy` edge before superseding the parent. Mark the original completed only when its full acceptance passed; otherwise record delivered and missing scope and supersede it honestly, or leave it open when dependencies cannot be updated. Never discard product requirements to close an issue.

5. **Validate and merge.** Run repository checks and every recorded acceptance test against the actual PR head. Gate merge on new or independently verified existing acceptance contracts, architecture invariants, core smoke and required CI. Select affected tests only with a proven dependency map; otherwise run the full applicable suite and preserve periodic full-suite coverage. An expected-red preimplementation test, zero executed required tests, or green focused repro after a failed gate is not passing evidence. Independently reverify fixture/harness changes that could alter coverage.
   Preserve the first failure's raw output, command, inputs and source revision; keep later runs separate. Capture bounded state at the failing operation/connection boundary before repeated retries; a green narrow repro cannot clear a failed required gate. Trust ordinary setup: investigate concrete environment failures and probe repairs cheaply, without imposing fingerprints or containers on working builds. Report each command separately from its wrapper/bookkeeping status, actual executed/pass/fail/skip counts and legitimate optional skips. If tests ran on uncommitted files, prove their byte identity after commit or rerun invalidated checks; never relabel the original revision or invent a passing gate. Prefer `coding-tooling run --report` when applicable. For Rust one-shot verification, use the installed disposable disk-maintenance wrapper where appropriate.
   Prefer **one targeted advisory Codex review** for substantive risky changes; skip it for docs, formatting, mechanical CI/dependency changes and Renovate PRs. Fix verified defects regardless of review label; unanswered P0/P1 findings block merge. Do not request another review merely because the SHA changed. Re-run `workctl pr <repo>#<n>`: repair `broken`, leave `waiting`, and merge only `ready` with `workctl merge` once independent acceptance also passes.
   **Approved non-executable instructions/Decisions** may be committed directly to default where permitted, or their existing documentation PR promptly merged after verifying its diff/head/protection. No CI, Codex review or independent acceptance handoff is required solely to record approved intent. This exception never applies to executable Markdown, generated artifacts, public-site sources, configuration, security enforcement or code; respect required approvals and branch protection.

6. **Verify publication and repeat.** Before queueing or merging a user-facing feature whose actual demo deploys afterward, record **Awaiting live deployment verification** on the original feature issue: PR/head, route, owner actions and expected outcomes. After merging, check the deployed revision and exercise the real journey. Record the live result and close only with actual evidence. If publishing is pending, unreachable, stale or broken, reopen/retain the **same feature issue** and revisit at a natural scan; never poll or create another queue. If a PR waits for external CI/review, do other in-scope work only; otherwise record the exact handoff and stop. Repeat while actionable work remains inside the owner's scope.

## Exceptional conditions

- **GitHub Actions billing/spending limit:** Only when **every** failed/missing check is independently identified as a billing-startup failure, and no other check is pending or failing, run all feasible workflow jobs locally at the PR head (prefer `act` one job at a time; otherwise run the steps). Record actual results and unavailable secrets/services on the PR. With all other acceptance, review and mergeability gates satisfied, `gh pr merge` may replace workctl; never use `--admin` or bypass branch protection. A job that started and failed is not an exception.
- **Usage limit:** Preserve existing agent/branch/PR and verify the former writer stopped before resuming. Recheck GitHub state; do not spawn competing workers. In Claude Code, interactive unattended `autoContinueAtUsageLimit` can resume at reset; background/`-p` workers do not wait, nor does a reset over 24 hours away.
- **Nothing actionable:** Invoke `unblock` only for an actual owner-only gap, otherwise stop.

## Report

Distinguish **implementation** (issue/PR state), **capability** (named checks and inputs at the actual revision) and **user-observable acceptance** (the real integrated/published result, or explicitly missing evidence). Never infer feature success merely from tests or a merge. For policy changes, assess `acceptance/product-selection.md` semantic scenarios separately from mechanical checks. Report one line per issue: `repo#n → merged PR #m | PR #m waiting on <x> | needs-decision | closed (reason)`, plus required owner actions.
